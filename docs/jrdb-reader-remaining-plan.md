## 2.6 仕様書との突き合わせ（2026-10-10 追記）

JRDB の仕様書と見本データ（[docs/jrdb-spec/](jrdb-spec/README.md)）を取得し、`test/spec.test.ts` で突き合わせた。

| 確認内容 | 結果 |
|---|---|
| リーダーのレコード長と、仕様書の項目表の長さ | 30 種すべて一致（BAC は仕様書見出しの 176 が誤りで、項目表・見本とも 184） |
| 見本データの取り込み | エラー 0、警告は見本データ自体の不整合 1 件のみ |
| リーダーが読む位置と長さ | 読んだ範囲はすべて仕様書の項目の中。項目名とコード側の列名も目視で全件照合し、食い違いなし |
| コード表（jrdb_code・特記・馬具・脚元・追い状態・調教コース・系統） | 全コードを変換できる |
| SED・KYI・HJC・OZ の値 | 仕様書の項目名で取り出した値と一致（SED 324 件、KYI 498 件、HJC 払戻 288 件） |
| JOA の厩舎BB印(90)・騎手BB印(101) の位置 | 仕様書で確認。現在の実装（offset 89, 100）で正しい |

見つかって直した不具合:

- **OZ の連勝オッズ**: 仕様書では「8頭立以下は枠連、9頭立以上は馬連」だが、常に馬連として保存していた。登録頭数で切り替えるようにした。
- **場コードが空白のレコード**: 前走データ（ZEC/ZED/ZKB）の外国・地方のレコードで `kaisai` が null になり、`TypeError` でファイル全体の取り込みが失敗していた（トランザクションで全件が取り消される）。開催が特定できないレコードは読み飛ばし、空白の場コードは警告しない。
- `KaisaiTool`: 場所・年月日が読めないときに、不正な ID を作らず null を返す。

コード表にない値が見本データに現れる箇所（取り込みでは null）:

- 印コード 7・8（KYI の総合印、万券印）、距離適性 4・7（KYG/KYH）。公式のコード表にはない。
- 地方の調教師の所属（北海・大井・笠松ほか）、産地名「追分」。

仕様書にあるが取り込んでいない項目（意図的なものを含む）: SED/SEC の調教師コード(328)、調教師名(163)、血統登録番号・馬名（KYI などで保存済み）、CSA/KSA の成績欄（リーディング・年別成績・コメント）、JOA の基準オッズ・回収率、KYI の前走キー群。

## 3. 実施順序

依存関係から次の順で進める。各ステップは独立してコミットする。

```
A. 移行方針の決定 ─┬─> B. 既存 DB の補正 ──┐
                   └─> (P1-16 の判断)      │
C. テスト基盤 ─────> D. P1-14 / P3 / コード表 ─> E. P2 の新規カラム ─> F. 新規リーダー・地方外国
                                                                       │
G. P0-10 トランザクション（独立。計測後）                              │
H. 再取り込み（B, D, E の後にまとめて 1 回）<───────────────────────────┘
```

再取り込みは時間がかかるため、ID やカラムを変える作業（A、B、E）を終えてから 1 回で済ませる。

## 4. ステップごとの内容

### A. 移行方針の決定（コード変更なし）

決めること:

1. **P1-16（タイムゾーン）**
   - 案1: `Date.UTC` に変えて環境依存をなくす。既存の開催 ID・レース ID・出走馬 ID がすべて変わるので、全件再取り込みが前提になる。
   - 案2: 現状維持。`TZ=Asia/Tokyo` を固定する運用にし、README に明記する。
   - 推奨は、既存 DB を作り直す予定があるなら案1、なければ案2。
2. **既存 DB の補正方法**
   - 案1: 該当テーブルを空にして再取り込み（確実。時間がかかる）。
   - 案2: 移行 SQL で補正（速いが、P0-1 で他場に上書きされた Kaisai 行は復元できない）。
   - 推奨は案1。Kaisai は BAC/KAB から作り直し、OddsHaitou は全件削除する。

### B. 既存 DB の補正

A で案2 を選んだ場合のみ作業する。案1 なら `migration/README.md` に手順を書くだけでよい。

- `migration/` の既存構成（`dialect`、`steps`、sqlite/mysql/postgresql の 3 本）に合わせて追加する。
- Kaisai: `Key = Key + Basho`、`Youbi` を再計算する。
- OddsHaitou: 全件削除（ID の体系が変わったため）。
- 3 系統の SQL を揃え、空の DB と既存の DB の両方で動作を確認する。

### C. テスト基盤（元の計画のフェーズ 0）

先に用意すると、以降の修正を安全に進められる。

1. `bun test` を使う。`test/fixtures/` には仕様書どおりに組み立てた合成レコードを置く。公式サンプルを使う場合はライセンスを確認する。
2. 最初に書くテスト（実施済みの修正の回帰防止を兼ねる）:
   - `Reader`: `readTime`、`readSignedInt`、`normalize`
   - `Codes`: 印、所属、輸送区分、追い状態、調教コース
   - ID 計算: 開催、開催キー、オッズ配当（`Kakutei.Kakutei` が次のレースと衝突しないこと）
   - `Hjc`: 3連複・3連単のオフセットと件数
3. DB に触れるテストは、インメモリの SQLite で `Tool.saveOrUpdate` の引数順を確認する。

### G. P0-10 トランザクション

単独のコミットにする。

1. 現在の取り込み時間を、代表的なデータセット（1 年分の KYI、SED）で計測する。
2. `transaction(async (manager) => ...)` にして `manager` を引き回す案と、`QueryRunner` で明示的に管理する案を比べる。DAO や各 Tool が `@OrmManager()` で持つ `entityManager` をどう差し替えるかが論点になる。

4. 失敗時にロールバックされること（途中の行が残らないこと）をテストで確認する。
